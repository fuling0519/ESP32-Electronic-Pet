# 韌體容量改善企劃（審閱草案）

- 日期：2026-10-01
- 負責：韌體組；前端組共同確認 BLE 相容性。
- 文件角色：2026-10-01 容量改善前的決策草案及原定階段，保留供回溯；不再維護即時進度。
- 實作與驗收只看 [主台帳 FW-CAP](project-plan.md#progress)；當日結果見 [建置紀錄](firmware-capacity-handoff.md)。下方「建議／待做」描述原計畫，不代表最新待辦。
- 目的：為 Deep Sleep、小遊戲及後續必要 BLE 擴充保留空間，同時讓前端沿用既有協定開發。

## 1. 改善前基線與原規劃

改善前 README 與主企畫記錄正式韌體為 1,216,921／1,310,720 bytes（92.8%），App 分割區剩 93,799 bytes，約 91.6 KiB。文件寫的約 93.8 KB 使用十進位單位。RAM 為 53,748 bytes（16.4%），這是靜態用量，不能代表 BLE 運行時的可用 heap。

本次修改前已重新 build 確認相同的 Flash／RAM 數字。改善前 firmware.bin 為 1,223,504 bytes；改善後數據見交接報告。兩者不能混用。

platformio.ini 固定目前平台與函式庫版本，未明訂自訂 partition table。src/ble/BleLink.cpp 原使用 Arduino BLEDevice、BLEServer、BLECharacteristic 與 BLE2902，現已遷移 NimBLE。對外協定為 BLE v1，唯讀命令、完整 JSON 快照及固定 16-byte JSON 分片。

改善前 Web 計畫與原始碼的 device_id 現況不一致。本次已補上固定 ID，並同步協定、Flutter 與 Web 計畫；歷史差異已修正。

## 2. 建議決策

先建立最新基線，再以獨立分支評估 NimBLE。以保持 BLE v1 對外行為相容為首要限制，不同時新增遠端命令、配對或更改存檔格式。

NimBLE 的節省幅度必須由本專案實際編譯決定，本企劃不預先承諾能省多少。若收益足夠且硬體相容驗收通過，再合入正式韌體。若不通過，保留現有 BLE，接著評估分割區。

建議初期目標：容量改善後，正常韌體的 App 分割區使用率不高於 80%。這是團隊待確認的工程預算，並非 ESP32 的技術限制，也不是已證明可以達到的結果。

## 3. F0：最新基線與兩組交接

韌體組在目前正常版建立可重現 build，記錄 commit／工作目錄差異、環境、Flash used／max、firmware.bin bytes、partition table、靜態 RAM。核對實機 Flash 大小與目前是否需要 OTA；不要僅依板型名稱推定。

在啟動後、未連線、BLE 已連線及持續通知後，量測 free heap、minimum free heap、largest free block；記錄可比較的測試時長與操作。啟動前後的差值用來辨識 BLE 運行成本。

兩組確認目前實際使用的協定／分支，尤其是 device_id 差異。保存可工作的前端版本及韌體產物，作為後續相容性比較依據。尚未通過 BLE 實機驗收時，先確認現有版本能正常連線，避免把既有問題誤判為遷移造成。

交付：最新容量報告、實際分割區、共同協定版本與現有 BLE 實機結果。前端 W0 使用這份報告，不負責代替韌體組改善容量。

## 4. F1：NimBLE 容量比較原型

在獨立分支／測試環境遷移 BleLink 的 BLE 底層，先核對 NimBLE 版本與目前 Arduino framework 的相容性並固定依賴版本。盡量保留現有 JSON 序列化、分片重組、命令處理與寵物邏輯。

相容性必須維持：廣播名稱及 Service UUID、Command 的 write with response、Event Notify 與訂閱行為、兩個查詢命令、v:1、既有欄位與型別、錯誤碼、4-byte 分片標頭、每片最多 16-byte JSON、1024-byte 訊息上限及既有逾時規則。

NimBLE 的 callback、CCCD、通知與重廣播行為需依選定版本實作，不能機械式替換類別名稱。容量比較時採相同產品功能、工具鏈與分割區，不以關閉必要功能製造節省結果。

交付：舊／新 build 的 Flash、靜態 RAM、heap 與功能差異報告。先完成編譯比較；硬體階段由使用者在核對測試環境後燒錄驗收。

## 5. F2：相容性驗收與合入

使用現有前端，驗收掃描、訂閱、查裝置資訊、查完整狀態、搖桿互動後通知、斷線再廣播及重連。確認中文分片重組、預設 MTU、錯誤封包、逾時與連續操作正常。

同時確認 OLED、輸入、音效、一般睡眠、重開機存檔、死亡與墓碑流程沒有退步；不用為遷移重新等待正式長時間疾病倒數，可使用既有快速測試環境驗證。

正常與既有快速測試環境均須編譯成功；硬體至少驗收正常版及涉及存檔／生命週期的代表環境。實測與僅編譯的項目分開記錄。合入後更新 README、主企畫與容量報告。

合入條件：明確量測收益、必要功能通過、前端無須因底層替換改協定。若仍未達 80% 目標，記錄差距並評估下一步，不假稱已滿足空間預算。

## 6. F3：必要時評估分割區

僅在 F1 收益不足、相容性不通過或未來功能仍放不下時啟動。按實機 Flash、NVS 需求與 OTA 需求比較更大的 OTA 雙槽和單 App／無 OTA 配置；不預先指定分割表。

先在獨立環境編譯比較。確認 NVS 的 offset／size、現有存檔保存及還原方法；變動分割區前備份資料並寫明遷移步驟。不得為增加程式空間任意縮小存檔區。

加大 App 分割區增加可容納大小，不會縮小程式或改善 RAM。若移除 OTA，需明確接受後續主要以 USB 更新的維護方式。更换大 Flash 板卡列為最後選項。

## 7. 改善後的功能順序與容量預算

先做 Deep Sleep，再做一個最小可玩的小遊戲。每项分開建置量測增量，避免睡眠、遊戲、BLE 遷移一次混在同一變更。

建議在 F2 後，把當時剩餘 App 空間的至多 25% 配給 Deep Sleep、至多 25% 配給第一個小遊戲，至少 50% 留給必要協定擴充、修正與後續成長。這是初期預算，F0／F1 有實際數據後再定案；不能當作功能需求已精確估算。

Deep Sleep：處理入睡存檔、BLE 結束連線、OLED／音效停止、Timer／GPIO26 喚醒、可信睡眠時長結算與重新初始化。避免在進入睡眠前送出現有前端不接受的 sleep 列舉；若需要 deep 狀態或預告通知，另提協定變更。首版前端可只顯示一般斷線與舊資料，不能憑斷線斷言裝置正在睡眠。

小遊戲：優先搖桿操作、程式繪圖與既有素材，採非阻塞更新。沿用現有寵物數值作結果回饋時不必新增 BLE 欄位；新遊戲紀錄、排名或手機控制另行協議。遊戲與 BLE 同時運行時量測 heap 與操作反應。

若任何功能超過預算，先查增量來源與素材／依賴成本，再縮減或調整方案；不以破壞存檔或直接刪除 BLE 功能換空間。

## 8. 分工與完成標準

韌體組：容量基線、NimBLE 原型、分割區決策、裝置行為及正常／測試環境量測。前端組：提供固定版本、協助 BLE 相容性測試、處理 Deep Sleep 斷線／重連 UI。共用協定由兩組一起確認。

容量改善與 device_id、saveGeneration、配對、遠端命令分開交付。BLE 底層更換若對外相容，不要求前端同步改版；新增欄位或行為則先更新 PROTOCOL.md 與相容策略，再分組實作。

完成標準：最新容量可重現、節省幅度有證據、已知前端正常運作、離線養成與存檔驗收通過，並有正式後續功能預算。未經實機驗收不得標記完整完成。
