# 神秘蛋電子寵物 Web 端分階段企劃

- 版本：1.1
- 日期：2026-10-01
- 範圍：承接現有 ESP32 NodeMCU-32S、BLE v1、Flutter Web companion 與 `device_id`。
- 文件角色：Web 需求、分工與驗收條件；本文不維護完成狀態。最新 W0～W8 與韌體進度只看 [主台帳](project-plan.md#progress)。

## 1. 企劃目標

提供玩家一個能登入帳號、綁定自己的電子雞、查看即時寵物狀態並保存陪伴紀錄的 Web 端。首個可交付版本優先支援手機或電腦瀏覽器在裝置附近連線；日後如需不在附近也能同步，再另行增加 ESP32 Wi-Fi 雲端連線階段。

網站不執行養成規則。ESP32 保有寵物資料及遊戲狀態的最終決定權；網站顯示裝置回報、管理雲端副本，並在已連線時提出受限的操作命令。

## 2. 開工依據

Web 組先讀 [主進度台帳](project-plan.md#progress) 的 BLE-S2、FW-CAP、APP-NATIVE 與 W0～W8，再讀 [共用協定](../esp32_pet_app/PROTOCOL.md)。實際容量由台帳連到最新有日期報告；本計畫不複製數字或完成宣告。

既有 Flutter 唯讀介面是開發基礎，不能推定登入、配對、事件、revision、saveGeneration 或雲端 API 已存在。SQLite schema 是邏輯模型參考，不是部署好的服務。

## 3. 首版建議架構

```text
ESP32 (BLE Peripheral)
        ⇅ Bluetooth Low Energy
已登入的 Web 瀏覽器 (BLE Central)
        ⇅ HTTPS API
Web 後端 ── PostgreSQL
```

瀏覽器在使用者明確選擇裝置後透過 Web Bluetooth 直接連線，讀取裝置 ID 與狀態。網頁將經驗證的資料透過 HTTPS API 寫入後端。帳號、擁有權、歷史紀錄及網站使用者介面都放在伺服器端，ESP32 只負責養成及 BLE 封包，不在有限的韌體 Flash 裡運行 Web Server、帳號系統或 SQL 資料庫。

目前 Web Bluetooth 有瀏覽器支援限制，並要求安全來源（HTTPS；本機開發可使用 localhost）。首版需將 Chrome 作為已知目標，以實際手機／電腦和 OS 確認 BLE 權限、斷線重連及部署環境。未支援 Web Bluetooth 的瀏覽器顯示清楚的相容性說明，將原生 App 列為未來替代方向；目前不顯示不存在的安裝連結。

此架構須明確接受一個產品限制：**首版的雲端同步由登入中的瀏覽器充當橋接器。** 網頁連上電子雞且有網路時才會上傳；使用者關閉網頁、離開藍牙範圍或 ESP32 斷電時，後端拿不到新狀態。歷史事件亦只有裝置或仍運行中的 App 曾保存，才可能完整補上。首版不得將它描述為全天候遠端監控。

如果產品需求要求關閉網頁後依然能遠端查看或照顧，需另做 Wi-Fi／MQTT over TLS／雲端架構。開始前先確認模組實際 Flash 與 OTA 分區；精簡 BLE 或更換 NimBLE 的效益與風險須實際編譯量測。可加大 App 分區，但須說明 OTA 分區縮小或移除的維護代價。**目前 NimBLE 已釋放空間，但仍不得未經 build 就假設 Wi-Fi/TLS 能容納且有足夠運行 RAM。**

## 4. 角色及核心資料流

### 玩家

以電子郵件或選定的身分提供者註冊／登入，連接附近的電子雞、確認裝置 ID 及綁定狀態，查看同步資料，管理帳號及解除綁定。

### 電子雞裝置

持續獨立養成並保存狀態。使用者透過實體操作開啟短暫的配對模式；裝置 ID 永久穩定，寵物 ID 隨個體而變，不代表登入帳號。

### 後端

負責身份驗證、裝置擁有權檢查、資料驗證、寵物及事件紀錄、命令稽核、速率限制與刪除流程。每一筆使用者資料查詢或修改都從伺服器登入 session 取得使用者身分，不接受客戶端自行指定 `userId` 作為授權依據。

### 狀態同步

1. Web 登入後請求連接附近 BLE 裝置。
2. ESP32 回報 `device_id` 與完整狀態快照。
3. Web 將 ID、目前寵物識別、revision 及資料傳給 HTTPS API。
4. 後端確認此帳號擁有裝置、欄位及 revision 合法，再保存最新狀態。
5. Web 顯示「裝置直連中」、「同步完成」或「最後同步時間」。

裝置回報為寵物數值的權威來源。後端收到時間 `receivedAt` 只表示伺服器收件時間，不能偽裝成可信出生、死亡或事件時間。若裝置無可信時鐘，保存 `ageSeconds` 及時間可信旗標，不推測真正斷電期間的時長。

### 帳號綁定

裝置 ID 不可單獨用於認領裝置。建議使用者在裝置上按鍵啟動限時綁定模式，ESP32 顯示一次性配對碼；已登入網頁輸入該碼，成功後後端建立唯一的 `user_id → device_id` 擁有關係，並使配對碼過期。裝置端需實作亂數、有效期限、重試上限、實體重啟配對及成功／逾時回饋。

配對憑證與防仿冒仍是安全設計的前置工作：Web Bluetooth 的「附近裝置連線」本身不會向後端證明裝置是真品。上線前定義設備如何安全產生或持有配對秘密、首次註冊如何驗證秘密，以及恢復出廠／轉移所有權的處理規則；不要把公開 `device_id`、MAC 或使用者輸入的寵物 ID 當作秘密。首版 prototype 可限測試帳號，未完成驗證前不得宣稱已具有強裝置防偽能力。

### 遠端操作

近距離首版由已登入的 Web 瀏覽器透過 BLE 送出命令；ESP32 仍依自己的養成邏輯檢查並執行，回傳結果及最新快照。Web 只在 ESP32 確認後顯示成功，並將發起帳號、命令 ID、結果和時間寫入稽核紀錄。未連線時不把餵食等操作排隊。

每個命令使用唯一 `commandId`、目標 `deviceId`、目標個體鍵、命令類別及效期；ESP32 端需拒絕過期、重複、已換寵物、不適用階段或死亡狀態的命令。藍牙斷線或結果不明時，顯示「結果待確認」，不可假設未執行或用新 ID 自動重送。

## 5. Web 首版範圍

### 必要功能

- 註冊、登入、登出、忘記密碼及刪除帳號流程。
- 個人裝置清單、連接／斷線、裝置 ID、韌體／協定版本與最後同步時間。
- 透過實體確認及限時配對碼綁定裝置；解除綁定與重新綁定流程。
- 顯示名字、寵物 ID、生命階段、飽食度、心情、清潔度、健康、有效年齡及睡眠。
- 明確標示線上直連、離線、等待資料、同步失敗及最後資料過期狀態。
- 裝置連線時執行餵食、清潔、治療；遵守韌體命令回覆、去重和命令有效期限。
- 已上傳之孵化、成長、生病、治療、死亡及領養事件時間軸。
- 已同步的歷代寵物與墓碑紀念館。
- 行動優先的響應式設計、鍵盤基本操作與清楚的 BLE 權限提示。

### 首版不做

持續背景同步、瀏覽器關閉後的遠端控制、AI 對話、社群／排行榜／商城、多寵物種類、感測器儀表板、OTA 管理、網站覆寫韌體養成狀態，以及無資料根據的事件補造。

## 6. 技術選型建議

- **前端**：沿用 `esp32_pet_app/` 的 Flutter Web UI 與現有 BLE 協定，新增網站頁面與登入狀態；確認 FlutterBluePlus Web 端行為適合目標瀏覽器。若遇到 Web Bluetooth 套件或瀏覽器限制，保留共用協定，改用原生 JavaScript Web Bluetooth adapter。
- **後端 API**：Node.js／TypeScript，HTTPS REST API；先採可部署的單體服務，不先拆微服務。
- **資料庫**：PostgreSQL；migration 管理 schema。既有 SQLite schema 可用作模型參考，須補充帳號擁有權、裝置配對、同步版本和唯一複合鍵後再轉換。
- **託管**：前端與 API 使用 HTTPS 部署；資料庫不公開網際網路直連，設定備份與資料保留政策。
- **BLE**：沿用既有 GATT UUID、16-byte JSON 分片與完整快照協定。協定每次擴欄位需考慮舊韌體、舊網頁與訊息長度。
- **Flash／RAM**：前端、圖鑑圖檔、歷史頁和帳號程式全留在 Web／伺服器。任何會增加 ESP32 韌體的功能須以 PlatformIO 實際 build 作為容量閘門，記錄 Flash、靜態 RAM 及可用 heap。

登入供應商、雲端平台、正式網域與預算在 W0 比較易部署及可供學校專題使用的方案後選定；不可把雲端服務免費額度或長期供應當成前提。

## 7. 資料模型與 API 草案

硬體 BLE 資料、Web domain、Web API 和雲端資料表必須是四個有 adapter／mapper 隔開的結構；依本節分層原則實作；獨立 Web 資料結構規格尚未建立，不引用不存在的文件。前端 UI 不讀取 BLE snake_case 欄位；ESP32 不認識登入帳號、資料庫 schema 或純 Web 偏好。

### 核心資料表

- `User`：帳號供應商識別、電子郵件（若需要）、建立／刪除時間；密碼如自建登入則只存經過適當 KDF 的 hash，不保存明文。
- `Device`：`device_id` 主鍵、產品／韌體／協定版本、建立時間、最後同步時間、綁定狀態。
- `DeviceOwnership`：`device_id`、`user_id`、建立／解除綁定時間、操作者；MVP 約束同一時間一台裝置只有一位 owner。
- `PairingSession`：短效配對碼的 hash、裝置候選 ID、到期時間、嘗試次數及使用狀態；禁止明文日誌。
- `Pet`：複合唯一鍵 `(device_id, save_generation, pet_id)`、名字、種類、階段、健康、三項需求、`age_seconds`、最後 revision、最新狀態。
- `PetEvent`：事件 ID、寵物複合鍵、事件種類、可信 `occurredAt`（可空）、`ageSeconds`、後端 `receivedAt`、來源及事件版本。
- `Command`：命令 ID、發起 user、device、目標個體、種類、狀態、效期、回應與稽核時間。
- `Memorial`：寵物複合鍵、死亡快照、可得事件、同步／刪除狀態；雲端墓碑不因裝置清檔自動刪除。

**身分鍵注意事項：**目前的 ESP32 `petId` 在寵物 NVS 完全重建後可能重用。正式保存歷代資料之前，韌體與 BLE 協定需加入 `saveGeneration`（建立新存檔時更新且不因更換寵物更新）或另外使用不可碰撞的個體 UUID。將此欄位視為雲端寵物歷史上線的先決條件，不能只以 `(device_id, pet_id)` 避免資料覆寫。

### API 路由草案

- `POST /v1/pairing-sessions`：登入使用者建立一次性綁定工作階段。
- `POST /v1/devices/claim`：交換有效實體配對證據並建立唯一擁有權。
- `GET /v1/devices`、`DELETE /v1/devices/{deviceId}/ownership`：列出與解除綁定。
- `PUT /v1/devices/{deviceId}/snapshot`：寫入經驗證、具版本的裝置快照；不可讓較舊 revision 覆蓋新資料。
- `POST /v1/devices/{deviceId}/events:batch`：去重補傳裝置／橋接器實際保存的事件。
- `POST /v1/devices/{deviceId}/commands`、`POST /v1/commands/{commandId}/result`：建立與回報遠端操作稽核資料。
- `GET /v1/pets`、`GET /v1/pets/{petKey}/events`、`GET /v1/memorials`：以伺服器登入身分限定查詢範圍。
- `DELETE /v1/account`：依明確保留政策刪除或匿名化使用者資料與綁定。

所有 API 驗證 schema、有效範圍、請求大小、session、權限與速率。裝置 ID 路徑參數不代表使用者有權存取該裝置。

## 8. 開發階段與里程碑

以一名熟悉 Flutter／Web／後端的開發者估算約 8～10 週；學生團隊依人力、雲端設定、瀏覽器／硬體驗收彈性調整。每階段需先通過驗收再擴大資料或控制範圍。

### W0：確認產品邊界與硬體基線（約 2～3 天）

- 確認本企劃首版為近距離 Web Bluetooth，由瀏覽器橋接雲端；界定離線、無藍牙與關閉網頁時網站顯示行為。
- 接收韌體組的 NimBLE＋device_id 容量基線與協定；韌體組負責重現 build、核對實機 Flash／分割區／OTA，Web 組共同完成瀏覽器相容驗收。容量改善不由 Web 組執行。
- 清點 Chrome Web 支援 OS／裝置，選出硬體驗收清單；確認 HTTPS、登入供應商及 API／DB 部署候選。
- 定義 Web v1 API、BLE 舊韌體相容原則、`saveGeneration` 方案與資料保留規則。

**驗收：**團隊可清楚說明首版有／無網路時可做什麼；接收並重現韌體組提供的 Flash/RAM 報告及操作流程。

Deep Sleep 與小遊戲由韌體組獨立開發。Deep Sleep 期間 BLE 斷線，醒來重新廣播；Web 首版維持最後資料並提示重連，不依斷線推斷睡眠。v1 的 sleep 仍只接受 awake／normal，未新增 deep 列舉。

### W1：BLE 唯讀硬體與瀏覽器驗收（約 1 週）

- 使用目前 GATT v1 連接 Web；顯示 `device_id`、完整寵物快照與接收時間。
- 測試掃描、授權、取消連線、實體按鍵造成的狀態變更、斷線、重連與舊韌體無 ID 的提示。
- 設計無藍牙／不支援瀏覽器時的引導頁，確認網站仍可在沒有硬體連線時瀏覽帳號資料。

**驗收：**選定的 Chrome／OS／板子組合至少連線、查狀態、斷線重連成功；離線養成不依賴網站。未過關時繼續唯讀排錯，不開遠端命令。

### W2：網站外殼、身份登入及開發環境（約 1 週）

- 加入首頁、登入／登出、我的裝置、帳號設定、空狀態、BLE 權限與錯誤頁。
- 建立 API、DB migration、開發／測試部署環境及 secret 管理。
- 定義 session cookie 或採用之 token 的保存、過期、登出、CSRF 防護與 CORS allowlist。

**驗收：**登入者可跨頁保持 session；登出後私有 API 拒絕存取；測試帳號之間資料隔離。

### W3：實體裝置配對與帳號綁定（約 1 週）

- 實作 ESP32 實體啟動配對窗口、短效碼產生及 UI 回饋；規劃碼的隨機性、猜測速率限制及重複使用防止。
- 後端加入裝置註冊、認領、擁有權唯一限制、解除綁定與原 owner 轉移流程。
- Web 顯示裝置 ID、型號／版本、綁定帳號及清楚的配對逾時／已認領錯誤。
- 完成威脅模型及配對證據的 server 驗證設計；公開 ID 僅作定位欄位，不當秘密。

**驗收：**有效配對只能成功一次且只能建立一位擁有者；逾時／錯誤／重放被拒絕；未經授權帳號無法讀取裝置；解除綁定即撤銷 API 權限。韌體如增加程式碼，build 後仍需在容量基線內並實測按鍵養成。

### W4：狀態上雲與首頁（約 1 週）

- 建立 Device、DeviceOwnership、Pet 最新快照模型及 `PUT snapshot` API。
- 接入 Web BLE 狀態通知，在連線且有網路時上傳；初版改以資料改變上傳，必要時低頻 heartbeat（如 30 秒，依耗電及流量測量決定）。
- 後端以 owner 權限及遞增 revision 做冪等更新；Web 首頁顯示三項需求、階段、健康、年齡、裝置直連／最後同步狀態。
- 將網路可用、BLE 連線和資料新鮮度分開呈現。

**驗收：**裝置與網站同一時點數值一致；重複、亂序或舊快照不回退資料；其他帳號無法讀取；網路中斷後 UI 清楚標示同步失敗並在恢復後同步最新狀態。

### W5：裝置端養成命令（約 1～2 週）

- 在 W1 唯讀實機驗收及 W3 授權流程過關後，才擴充 BLE 命令協定與 ESP32 去重處理。
- Web 只提供餵食、清潔、治療操作；後端先驗證 owner，再簽發／允許有目標和有效期限的命令資料，瀏覽器經 BLE 轉送 ESP32。
- ESP32 使用既有遊戲邏輯判斷可否操作，保存狀態後回傳結果與 revision；Web 僅在收到裝置成功結果後顯示完成。
- 定義結果待確認、命令過期、目標寵物已更換、蛋／死亡狀態拒絕、同命令重播等 UI 與協定行為。

**驗收：**相同 command ID 最多執行一次；失去回覆不會顯示成功；新寵物不會收到舊命令；無 owner 權限或離線時命令不執行；OLED、NVS、三項狀態與網站結果一致。遠端命令增加的 Flash/RAM 每個環境皆記錄。

### W6：成長事件、寵物歷史與紀念館（約 1 週）

- 確認並實作 `saveGeneration`／個體 UUID，完成資料庫複合鍵及舊資料遷移策略。
- 以裝置實際上報事件建立成長時間軸；標明事件來源、`ageSeconds`、可信發生時間與伺服器收到時間。
- 保存已同步墓碑及舊寵物歷史；使用明確刪除／保留政策，不在領養新蛋時覆蓋舊雲端寵物。
- 未曾上報或被裝置刪除的紀錄呈現缺漏，不虛構歷史日期或操作。

**驗收：**裝置重開、重新領養與同步重試都不重複建個體／墓碑；存檔代次改變時不覆蓋舊寵物；未知時間區段明確呈現未知。

### W7：上線品質、隱私與展示驗收（約 1 週）

- 補齊權限、綁定濫用、命令重放、API 輸入、session、rate limit、secret、DB 備份／恢復檢查。
- 完成小螢幕／桌面響應式、鍵盤焦點、錯誤訊息、載入與空狀態、頁面刷新和瀏覽器重新授權流程。
- 設置錯誤率、API 健康狀態和同步結果的基本監控；制定個資刪除、保留期限及操作說明。
- 用正常版韌體完成完整展示彩排與需求驗收。

**驗收：**兩個不同帳號完整隔離；未授權裝置不能綁定／讀取／操作；重複命令無副作用；斷網和關閉頁面不會顯示假成功；安全部署只使用 HTTPS，操作文件足以讓新使用者完成登入、配對及解除綁定。

### W8（選配）：常駐 Wi-Fi 雲端同步評估

僅在「不開 Web、人在遠處仍需查看／照顧」成為已確認需求時啟動。比較 BLE＋Wi-Fi 同時存在、以 Wi-Fi 取代 BLE、手機原生 App 作 bridge、換用較大 Flash 的 ESP32 板卡等方案。先做一個量測原型，確認持續連線耗電、Wi-Fi 設定、安全憑證、斷網重試、Flash/RAM、OTA 回復及睡眠喚醒需求，再形成獨立工期與硬體決策。

## 9. MVP 驗收展示流程

1. 建立帳號並登入。
2. 於電子雞實體啟動限時配對，Web 連 BLE 後確認裝置 ID、輸入配對碼並綁定。
3. 網站顯示同一隻小鳥的三項需求、健康、階段與有效年齡。
4. 轉動搖桿或等待養成數值改變，Web 收到快照並完成雲端同步。
5. 網站送出餵食請求，查看 ESP32 OLED、狀態和命令結果一致。
6. 關閉瀏覽器或中斷網路，展示「最後同步」以及裝置仍可離線養成；恢復網路與連線後更新狀態。
7. 展示成長事件、已同步歷代寵物與解除綁定。

不得把本地展示假資料標成真實硬體資料；測試配對碼或測試韌體需明確標示。

## 10. 主要風險與處理

- **Flash 空間不足**：讓雲端及 UI 都在外部，ESP32 擴充保持小型協定；各韌體 PR 記錄 image bytes、App 分區餘額、靜態 RAM 與可用 heap；變更 BLE stack 或 partition 先用獨立 branch build 比較，不直接燒錄測試板。
- **瀏覽器 BLE 支援與權限差異**：選定實際支援組合、HTTPS 部署與 UI 降級提示；把 BLE adapter 與頁面資料層分離，保留未來原生 App 接同一 API 的路徑。
- **Web 關閉即停止同步**：同步頁清楚說明；不把 receivedAt 誤作即時在線或寵物實際事件時間。若不能接受，啟動 W8。
- **公開 `device_id` 被冒用**：配對使用實體確認與可驗證一次性證據，後端所有資料操作再查 owner；ID 本身不提供權限。
- **BLE 中斷與重複命令**：命令 ID、效期、目標個體、ESP32 去重和待確認狀態一起驗收。
- **時間線缺漏**：韌體／橋接器需把重要事件存在有限容量佇列並回報溢位；網站如無事件只顯示狀態快照，標示紀錄不完整。
- **`petId` 重用**：以 save generation 或 UUID 建立穩定個體鍵後才正式上線歷史／紀念館。

## 11. 成功指標

- 新手可依 UI 完成註冊、裝置實體配對及確認綁定，不需手動操作資料庫。
- 所有裝置和寵物資料請求都通過 server-side owner 權限檢查。
- 在選定瀏覽器與硬體環境，狀態同步穩定、舊 revision 不覆蓋新資料，錯誤／離線狀態可理解。
- 命令只有經 ESP32 回覆成功才在網站標成成功；重播同一命令不重複執行。
- ESP32 離線遊戲不因 Web、API、資料庫或家用 Wi-Fi 故障而中止。
- Flash 使用量有最新、可重現的 build 結果；未經容量量測不把新韌體功能併入發行版。
